# Ответы на вопросы

## 1. Где должна находиться проверка владельца заметки: в контроллере, сервисе или репозитории?

Решение о том, что чужую заметку трогать нельзя, принимает **сервис** — это правило предметной
области. Физически оно исполняется **в репозитории, внутри предиката запроса**: `userId` —
обязательный аргумент, и строка, ему не принадлежащая, просто не находится. Контроллер к
проверке отношения не имеет, он только достаёт `userId` из аутентифицированного запроса и
переводит результат в HTTP.

Почему не в контроллере: контроллер — это один из транспортов. Тот же сервис завтра дёрнут из
консольной команды, обработчика очереди или GraphQL-резолвера, и проверка, живущая в
HTTP-слое, туда не поедет. Проверка, которую можно обойти, зайдя с другой стороны, — это не
проверка.

Почему не «только в репозитории»: репозиторий не должен знать, что означает отсутствие строки —
`404`, пустой список или молчаливый пропуск. Он возвращает `null`, а сервис решает, что это
значит. Иначе слой данных начинает разговаривать HTTP-статусами.

Ключевой момент: **проверка и запись — это одна операция, а не две**. Как только владение
становится отдельным `if` перед `update`, появляется возможность написать `update` без этого
`if`. Здесь такой возможности нет: сигнатура `updateOwned(userId, noteId, payload)` не даёт
сделать запрос, не назвав владельца.

## 2. Как избежать ситуации, когда пользователь меняет чужую заметку?

Пять уровней, и первый — главный:

1. **Владение — часть условия записи.** `UPDATE … WHERE id = $1 AND user_id = $2`. Ноль
   затронутых строк → `404`. Не «прочитать, сравнить, записать»: между чтением и записью есть
   окно, и код с двумя шагами всегда можно случайно сократить до одного.
2. **`userId` только из проверенного токена.** Не из body, не из query, не из пути. В API его
   вообще нет — подменять нечего.
3. **Белый список изменяемых полей.** DTO пропускает только `title` и `content`
   (`whitelist` + `forbidNonWhitelisted`), а сервис ещё раз пересобирает патч поле за полем:
   типы стираются в рантайме, и объект, пришедший из транспорта, может нести лишние ключи.
   Без этого `{"userId": "чужой-id"}` в теле переписал бы владельца.
4. **Ответ не различает «нет» и «чужая».** Иначе владение утекает через коды ответов.
5. **Ограничение на уровне БД.** Внешний ключ на `users`, а в системе с несколькими сервисами,
   ходящими в одну базу, — ещё и RLS в Postgres с политикой по `current_setting('app.user_id')`.
   Это последний рубеж на случай, если ошибка проедет через все предыдущие.

Проверяется это тестами, которые смотрят не только на исключение, но и на данные: после отказа
чужая заметка должна остаться неизменной (`tests/update-note.test.ts`).

## 3. Какой HTTP-статус лучше вернуть при попытке открыть чужую заметку?

**404.** `403` сообщает «ресурс существует, но он не твой», и перебор идентификаторов
превращается в разведку: можно узнать, какие заметки вообще есть в системе, у кого их много,
когда появилась новая. Для приватного ресурса правильный ответ — «для тебя такого объекта нет».
Соответственно, «чужая» и «несуществующая» должны отвечать **побайтово одинаково**: одинаковый
код, одинаковое тело. Отдельным тестом проверяю именно это.

Оговорка. `403` уместен, когда сам факт существования ресурса не является секретом: общий
воркспейс, где список объектов виден всем, а редактировать может только автор. Там `404` вместо
`403` только запутает пользователя — он же видит объект на экране. Здесь не тот случай: заметки
приватные, чужие `id` пользователь неоткуда взять не может.

И отдельно `401` — когда пользователь не аутентифицирован вообще. Это другой ответ: «представься»,
а не «такого нет».

## 4. Какие поля разрешено изменять пользователю?

Только `title` и `content`.

`id` — идентификатор, менять его значит подменять объект. `userId` — владение, оно вообще не
предмет пользовательского редактирования. `createdAt` — исторический факт. `updatedAt` — ставит
система, иначе поле перестаёт что-либо значить.

Важно, что список **белый, а не чёрный**. Чёрный список ломается молча: добавили в модель
`isPinned` или `deletedAt`, забыли дописать запрет — и поле стало редактируемым. Поэтому патч
типизирован собственным типом `NoteUpdatePayload`, а не `Prisma.NoteUpdateInput`: новое поле в
схеме не станет изменяемым само по себе, для этого придётся осознанно расширить тип.

Отдельно про `content`: `null` — легальное значение и означает «очистить», а отсутствие ключа —
«не трогать». Для `title` `null` запрещён: поле обязательное, очищать его нечем.

## 5. Нужна ли транзакция при обновлении одной заметки?

Нет. Один `UPDATE` — уже атомарная операция, транзакция вокруг него ничего не добавляет, кроме
лишнего раунд-трипа.

Транзакция понадобится, как только вместе с заметкой меняется что-то ещё в той же базе:
запись в журнал изменений, счётчик заметок у пользователя, строка в outbox для события
`note.updated`. Тогда «заметка изменилась, а событие не отправилось» — это уже рассогласование,
и его надо закрывать одной транзакцией.

Второй случай — read-modify-write, когда новое значение считается из старого. Например,
редактирование с версионированием: `WHERE id = $1 AND user_id = $2 AND version = $3`, при нуле
затронутых строк — `409`. Здесь тоже можно обойтись без явной транзакции, потому что условие
уезжает в сам `UPDATE`; транзакция нужна, только если между чтением и записью появляется код на
стороне приложения.

## 6. Какие индексы стоит добавить в PostgreSQL?

Из схемы (`prisma/schema.prisma`, готовый DDL — `prisma/schema.sql`):

- `notes_pkey` на `notes(id)` — приходит с первичным ключом, обслуживает чтение и запись по `id`.
- `users_email_key` — уникальный индекс на `users(email)`, он же гарантия уникальности почты.
- **`notes(user_id, created_at DESC, id DESC)`** — рабочая лошадка. Один индекс закрывает три
  вещи сразу: фильтр `WHERE user_id = $1`, сортировку `ORDER BY created_at DESC, id DESC` (без
  отдельного шага сортировки) и курсорную пагинацию.

Про внешний ключ отдельно: Postgres **не создаёт** индекс под FK автоматически. Без индекса,
начинающегося с `user_id`, удаление пользователя с `ON DELETE CASCADE` заставило бы базу
просканировать всю таблицу заметок. Здесь композитный индекс начинается с `user_id` и закрывает
этот случай — отдельный индекс только на `user_id` был бы дублирующим.

Чего сознательно нет: индекса под сортировку по `updated_at` (такой сортировки в API нет) и
индекса под поиск по тексту (поиска в API нет). Каждый индекс — это замедление записи и
занятое место; их добавляют под конкретный запрос, а не «на всякий случай».

## 7. Что изменится, если заметок у пользователя будет несколько миллионов?

Сломается в первую очередь то, что на маленьких данных работало случайно:

- **Пагинация по `OFFSET`** деградирует линейно: чтобы отдать страницу с миллионным смещением,
  Postgres прочитает и выбросит миллион строк. Поэтому в API сразу курсор, а не `page`.
- **`COUNT(*)` для `total`** становится полным проходом по индексу. Либо убрать счётчик из
  контракта, либо отдавать оценку (`reltuples` из `pg_class`, либо счётчик, поддерживаемый
  отдельно).
- **Поиск по `LIKE '%текст%'`** индексом не покрывается вообще. Нужен GIN: `pg_trgm` для поиска
  по подстроке или `tsvector` для полнотекстового. На больших объёмах — отдельный поисковый
  индекс за пределами Postgres.
- **Один тяжёлый запрос не должен ронять остальных.** Жёсткий потолок `limit`, `statement_timeout`
  на пул, ограничение размера тела запроса.
- **Обслуживание таблицы.** Autovacuum с настройками под большую таблицу, иначе раздувание
  индексов; при желании — партиционирование (по `user_id` хешем, если нагрузка размазана, или по
  времени, если старые заметки читают редко).

И главное — вопрос «а откуда у одного пользователя миллионы заметок». Если это импорт или
интеграция, то заметки перестают быть «заметками» в исходном смысле, и модель, скорее всего,
надо пересматривать: архивные и активные записи живут по разным правилам.

## 8. Как бы вы добавили кеширование через Redis?

Сначала — измерил бы. Чтение по первичному ключу из Postgres с прогретым кешем страниц стоит
доли миллисекунды; кеш перед таким запросом чаще добавляет сложность и класс багов, чем
скорость. Реальные кандидаты — не «заметка по id», а горячие агрегаты и списки.

Если кеш всё-таки нужен:

- **Ключ обязан включать `userId`**: `notes:{userId}:{noteId}`. Ключ без владельца превращает
  кеш в канал утечки — первый, кто прогрел ключ, отдаёт свои данные следующему.
- **Инвалидация — в том же месте, где происходит запись**, и после успешного коммита. Не по
  таймеру и не «где-нибудь потом».
- **TTL как страховка**, а не как основной механизм: он ограничивает время жизни рассинхрона,
  если инвалидацию где-то забыли.
- **Гонка «прочитал старое → записал в кеш уже после инвалидации»** — реальная. Лечится либо
  версией в ключе (`notes:{userId}:v{n}`, при записи версия инкрементится, старые ключи
  протухают сами), либо коротким TTL, если можно потерпеть.
- **Списки кешировать сложнее**, чем отдельные записи: любая запись инвалидирует все страницы
  пользователя. Кешировать имеет смысл только первую страницу — её читают на порядок чаще.

Чего бы точно не делал: не клал бы в кеш результат проверки владения. Права должны проверяться
по актуальному состоянию.

## 9. В каких случаях здесь мог бы пригодиться Socket.IO?

- **Несколько устройств у одного пользователя.** Заметка открыта на ноутбуке и телефоне;
  изменение с одного устройства должно приехать на другое без перезагрузки страницы.
- **Совместное редактирование.** Тут одного сокета мало — нужен CRDT или OT, иначе два
  одновременных редактора будут затирать друг друга. Сокет здесь только транспорт.
- **Presence и «кто-то печатает»** — состояние, которое живёт секунды и не имеет смысла в базе.
- **Уведомление о завершении долгой операции**: импорт, экспорт, массовое удаление. Клиенту не
  нужно опрашивать статус.

Что важно не забыть: **сокет не наследует авторизацию HTTP-слоя автоматически**. Комната должна
быть привязана к `userId`, а вход в комнату по `noteId` — проверять владение ровно так же, как
это делает `PATCH`. Иначе появляется второй, никем не охраняемый вход к тем же данным.

И трезво: для односторонней доставки обновлений SSE проще — меньше состояния, переживает
обычный HTTP-прокси. Socket.IO стоит брать, когда нужен именно двусторонний обмен.

## 10. Какие части решения вы бы покрыли тестами в первую очередь?

Инварианты, а не CRUD-обвязку. Порядок такой:

1. **Чужую заметку изменить нельзя** — и проверять надо не только исключение, но и то, что
   данные чужой заметки не изменились. Тест, который смотрит только на тип ошибки, пройдёт и на
   коде, который сначала пишет, а потом падает.
2. **«Чужая» и «несуществующая» отвечают одинаково** — иначе владение утекает через ответы.
3. **Изменяются только разрешённые поля** — с враждебным патчем, несущим `userId` и `id`.
4. **Частичное обновление**: непереданные поля не затираются, явный `null` очищает.
5. **Ошибки базы не маскируются под `404`** — иначе `P2002` или обрыв соединения превратится в
   «не найдено» и реальная проблема станет невидимой.
6. Дальше — пагинация: граница страницы, стабильность порядка при одинаковом `created_at`.

Про уровень. Всё перечисленное здесь покрыто быстрыми тестами против подменённого клиента
Prisma — они ловят логику, но не проверяют настоящий SQL. Поэтому минимум один интеграционный
тест против живого Postgres обязателен: он проверяет, что предикат владения действительно
доехал до базы, а индекс используется. Реальную базу в этом задании не поднимаю (это в
ограничениях), поэтому граница честно обозначена в комментарии к тестовому стенду.

Чего бы не тестировал: что Prisma умеет обновлять строку, что Nest вызывает контроллер, что
валидатор проверяет длину строки. Это тесты чужого кода.

Насколько тесты вообще что-то ловят, проверено мутационным прогоном: в рабочий код по одному
вносятся 12 дефектов (снятие владения из предиката, `403` вместо `404`, копирование патча
целиком, подмена любой ошибки базы на `404` и другие) — каждый роняет прогон.
`npm run test:mutation`.
