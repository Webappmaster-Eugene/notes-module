# API модуля заметок

## Общие правила

Все эндпоинты требуют аутентифицированного пользователя. Гард кладёт проверенного пользователя в
`request.user`, и userId берётся только оттуда. Ни в пути, ни в параметрах запроса, ни в теле
userId не появляется: чего нет в контракте, то нельзя подменить. Сам гард за рамками задания, см.
`src/common/current-user-id.decorator.ts`.

Идентификаторы - UUID версии 7. Некорректный UUID в пути отсекается на границе и не доезжает до
базы. Иначе Postgres упал бы на приведении типа и клиент получил бы 500 вместо 400.

Ошибка всегда приходит в одном виде, HTTP-статус стоит в статус-строке:

```json
{ "code": "NOTE_NOT_FOUND", "message": "Note not found" }
```

Ошибки проверки тела дополнительно несут поле details:

```json
{
  "code": "VALIDATION_FAILED",
  "message": "Request validation failed",
  "details": [
    {
      "field": "title",
      "constraints": ["title must be shorter than or equal to 200 characters"]
    }
  ]
}
```

Коды ошибок:

| HTTP | code | Когда |
| ---- | ---- | ----- |
| 400 | VALIDATION_FAILED | тело не прошло проверку или содержит поле вне белого списка |
| 400 | INVALID_NOTE_ID | noteId в пути не является UUID |
| 400 | INVALID_CURSOR | курсор постраничной выборки не разбирается |
| 400 | EMPTY_PATCH | PATCH не содержит ни одного изменяемого поля |
| 401 | UNAUTHENTICATED | токена нет, он истёк или не проходит проверку подписи |
| 404 | NOTE_NOT_FOUND | заметки не существует или она принадлежит другому пользователю |
| 429 | RATE_LIMITED | превышен лимит запросов |
| 500 | INTERNAL_ERROR | необработанная ошибка, детали уходят только в лог |

Ограничения полей. Заголовок обязателен, от 1 до 200 после обрезки пробелов. Содержимое - строка
до 50 000 либо null. Длина считается в единицах UTF-16, как её видит JavaScript, а `VARCHAR(200)`
в Postgres считает символы. Строка из эмодзи упрётся в лимит API вдвое раньше, чем в лимит
колонки. Расхождение в безопасную сторону: до ошибки базы дело не дойдёт.

Заметка выглядит одинаково во всех ответах:

```json
{
  "id": "019706f0-0000-7000-8000-00000000b001",
  "title": "Список покупок",
  "content": "молоко, хлеб",
  "createdAt": "2026-06-01T10:00:00.000Z",
  "updatedAt": "2026-06-04T12:00:00.000Z"
}
```

Поля userId в ответе нет намеренно. Все заметки в выдаче и так принадлежат вызывающему, а лишнее
поле - это лишнее обязательство контракта, убрать его потом будет ломающим изменением.

## Создать заметку

`POST /notes`

Тело: `{ "title": "Список покупок", "content": "молоко, хлеб" }`, содержимое необязательно.

Ответ 201 Created, заголовок `Location: /notes/{id}`, тело - представление заметки.

Ошибки: 400 VALIDATION_FAILED, 401 UNAUTHENTICATED, 429 RATE_LIMITED.

Повторная отправка создаст вторую заметку, и это осознанно. Если бы дубли были проблемой,
например при повторных попытках мобильного клиента, я бы принимал заголовок `Idempotency-Key` и
вешал уникальный индекс на пару `(user_id, idempotency_key)`, а не пытался угадывать дубль по
содержимому.

## Получить список своих заметок

`GET /notes`

Параметры запроса: `limit` от 1 до 100, по умолчанию 20, потолок жёсткий; `cursor` - непрозрачная
строка из поля nextCursor предыдущего ответа.

Ответ 200 OK:

```json
{
  "items": [
    {
      "id": "019706f0-0000-7000-8000-00000000b001",
      "title": "Список покупок",
      "content": "молоко, хлеб",
      "createdAt": "2026-06-01T10:00:00.000Z",
      "updatedAt": "2026-06-04T12:00:00.000Z"
    }
  ],
  "nextCursor": "eyJjcmVhdGVkQXQiOiIyMDI2LTA2LTAxVDEwOjAwOjAwLjAwMFoifQ"
}
```

Когда страниц больше нет, nextCursor равен null.

Выборка идёт по курсору, а не по смещению. `OFFSET 1000000` заставляет Postgres прочитать и
выбросить миллион строк, и чем дальше страница, тем медленнее ответ. Курсор - это пара
`(createdAt, id)` последней отданной строки, запрос ложится ровно на индекс
`notes(user_id, created_at DESC, id DESC)`. Поле id в ключе обязательно: created_at не уникален,
и без второго поля строки с одинаковой меткой времени могли бы задваиваться или теряться на
границе страниц.

Общего числа заметок в ответе нет. `COUNT(*)` по большой таблице стоит полного прохода по
индексу. Если счётчик понадобится, это отдельный эндпоинт с приблизительной оценкой.

Ошибки: 400 VALIDATION_FAILED, 400 INVALID_CURSOR, 401 UNAUTHENTICATED, 429 RATE_LIMITED.

## Получить одну заметку

`GET /notes/{noteId}`

В условии задания этой операции нет, но без неё клиент не может открыть заметку по ссылке.

Ответ 200 OK, тело - представление заметки.

Ошибки: 400 INVALID_NOTE_ID, 401 UNAUTHENTICATED, 404 NOTE_NOT_FOUND.

## Изменить заметку

`PATCH /notes/{noteId}` - единственная реализованная операция, код в `src/notes/`.

Метод PATCH, а не PUT. PUT означает замену ресурса целиком, то есть клиент обязан прислать все
поля. Клиент, который правит только заголовок, вынужден был бы сначала прочитать заметку и
отправить её обратно, а по дороге затёр бы чужое изменение содержимого.

Тело: хотя бы одно из полей `{ "title": "Новый заголовок", "content": "новое содержимое" }`.
Значение null в поле content очищает содержимое. Отсутствие ключа означает «не трогать», и API
различает эти два случая.

Ответ 200 OK, тело - представление заметки после изменения.

Ошибки: 400 VALIDATION_FAILED, 400 EMPTY_PATCH, 400 INVALID_NOTE_ID, 401 UNAUTHENTICATED,
404 NOTE_NOT_FOUND.

Чужая заметка отвечает 404, а не 403. Ответ 403 подтвердил бы, что заметка с таким id
существует, и перебор идентификаторов превратился бы в разведку чужих данных. Подробнее - в
[ANSWERS.md](./ANSWERS.md), вопрос 3.

## Удалить заметку

`DELETE /notes/{noteId}`

Ответ 204 No Content, тела нет.

Ошибки: 400 INVALID_NOTE_ID, 401 UNAUTHENTICATED, 404 NOTE_NOT_FOUND.

Повторное удаление отвечает 404. Требование повторяемости DELETE при этом не нарушается:
состояние системы после второго вызова то же самое. Отвечать 204 всегда тоже допустимо, но тогда
клиент не отличит «удалил» от «такого никогда не было», а это как раз тот сигнал, который
помогает ловить рассинхрон на клиенте.

## Чего в API нет намеренно

Совместного доступа к заметкам, тегов и папок, поиска по тексту, корзины и восстановления, версий
и истории изменений, экспорта. Каждое из этого меняет модель данных и права доступа, а добавлять
их на всякий случай значит проектировать вслепую.
