# API модуля заметок

## Общие правила

**Аутентификация.** Все эндпоинты требуют аутентифицированного пользователя. Гард кладёт
проверенного пользователя в `request.user`, и `userId` берётся только оттуда. Ни в пути, ни в
query, ни в теле `userId` не появляется — иначе у клиента возник бы способ его подменить.
Реализация гарда за рамками задания (см. `src/common/current-user-id.decorator.ts`).

**Идентификаторы.** UUID (v7). Некорректный UUID в пути отсекается на границе и не доезжает до
базы: иначе Postgres упал бы на приведении типа и клиент получил бы `500` вместо `400`.

**Формат ошибки.** Одинаковый для всего модуля, HTTP-статус — в статус-строке:

```json
{ "code": "NOTE_NOT_FOUND", "message": "Note not found" }
```

Ошибки валидации дополнительно несут `details`:

```json
{
  "code": "VALIDATION_FAILED",
  "message": "Request validation failed",
  "details": [{ "field": "title", "constraints": ["title must be shorter than or equal to 200 characters"] }]
}
```

| HTTP | `code`               | Когда                                                              |
| ---- | -------------------- | ------------------------------------------------------------------ |
| 400  | `VALIDATION_FAILED`  | тело не прошло валидацию или содержит поле вне белого списка         |
| 400  | `INVALID_NOTE_ID`    | `noteId` в пути не является UUID                                     |
| 400  | `INVALID_CURSOR`     | курсор пагинации не разбирается                                      |
| 400  | `EMPTY_PATCH`        | `PATCH` не содержит ни одного изменяемого поля                       |
| 401  | `UNAUTHENTICATED`    | токена нет, он истёк или не проходит проверку подписи                |
| 404  | `NOTE_NOT_FOUND`     | заметки не существует **или** она принадлежит другому пользователю   |
| 429  | `RATE_LIMITED`       | превышен лимит запросов                                              |
| 500  | `INTERNAL_ERROR`     | необработанная ошибка; детали уходят только в лог                    |

**Ограничения полей.** `title` — обязательная строка, 1–200 после обрезки пробелов. `content` —
строка до 50 000 либо `null`. Длина считается в единицах UTF-16, как её видит JavaScript, тогда
как `VARCHAR(200)` в Postgres считает символы: строка из эмодзи упрётся в лимит API вдвое раньше,
чем в лимит колонки. Расхождение в безопасную сторону — до ошибки базы дело не дойдёт.

**Представление заметки** (одинаково во всех ответах):

```json
{
  "id": "019706f0-0000-7000-8000-00000000b001",
  "title": "Список покупок",
  "content": "молоко, хлеб",
  "createdAt": "2026-06-01T10:00:00.000Z",
  "updatedAt": "2026-06-04T12:00:00.000Z"
}
```

`userId` в ответе нет намеренно: все заметки в выдаче и так принадлежат вызывающему, а лишнее
поле — это лишнее обязательство контракта.

## 1. Создать заметку

`POST /notes`

**Тело**

```json
{ "title": "Список покупок", "content": "молоко, хлеб" }
```

`content` необязателен.

**Ответ `201 Created`**, заголовок `Location: /notes/{id}`, тело — представление заметки.

**Ошибки:** `400 VALIDATION_FAILED`, `401 UNAUTHENTICATED`, `429 RATE_LIMITED`.

Повторная отправка создаст вторую заметку — это осознанно. Если бы дубли были проблемой
(ретраи мобильного клиента), я бы принимал заголовок `Idempotency-Key` и вешал уникальный
индекс на `(user_id, idempotency_key)`, а не пытался угадывать дубль по содержимому.

---

## 2. Получить список своих заметок

`GET /notes`

**Query**

| Параметр | Тип    | По умолчанию | Описание                                   |
| -------- | ------ | ------------ | ------------------------------------------ |
| `limit`  | number | `20`         | 1–100, потолок жёсткий                     |
| `cursor` | string | —            | непрозрачный курсор из `nextCursor`        |

**Ответ `200 OK`**

```json
{
  "items": [{ "id": "…", "title": "Список покупок", "content": "молоко, хлеб", "createdAt": "…", "updatedAt": "…" }],
  "nextCursor": "eyJjcmVhdGVkQXQiOiIyMDI2LTA2LTAxVDEwOjAwOjAwLjAwMFoiLCJpZCI6IjAxOTcwNmYwLTAwMDAtNzAwMC04MDAwLTAwMDAwMDAwYjAwMSJ9"
}
```

`nextCursor` равен `null`, когда страниц больше нет.

Пагинация курсорная, а не по `offset`: `OFFSET 1000000` заставляет Postgres прочитать и
выбросить миллион строк, и чем дальше страница, тем медленнее. Курсор — это `(createdAt, id)`
последней отданной строки; запрос ложится ровно на индекс
`notes(user_id, created_at DESC, id DESC)`. `id` в ключе обязателен: `created_at` не уникален,
и без второго поля строки с одинаковой меткой времени могли бы задваиваться или теряться на
границе страниц.

`total` не возвращается: `COUNT(*)` по большой таблице стоит полного прохода по индексу. Если
счётчик понадобится — отдельный эндпоинт с приблизительной оценкой.

**Ошибки:** `400 VALIDATION_FAILED`, `400 INVALID_CURSOR`, `401 UNAUTHENTICATED`, `429 RATE_LIMITED`.

---

## 3. Получить одну заметку

`GET /notes/{noteId}`

В условии задания этой операции нет, но без неё клиент не может открыть заметку по ссылке.

**Ответ `200 OK`** — представление заметки.

**Ошибки:** `400 INVALID_NOTE_ID`, `401 UNAUTHENTICATED`, `404 NOTE_NOT_FOUND`.

---

## 4. Изменить заметку

`PATCH /notes/{noteId}` — **единственная реализованная операция**, см. `src/notes/`.

`PATCH`, а не `PUT`: `PUT` означает замену ресурса целиком, то есть клиент обязан прислать все
поля. Клиент, который редактирует только заголовок, вынужден был бы сначала прочитать заметку и
отправить её обратно — и по дороге затёр бы чужое изменение содержимого.

**Тело** — хотя бы одно из полей:

```json
{ "title": "Новый заголовок", "content": "новое содержимое" }
```

`content: null` очищает содержимое. Отсутствие ключа означает «не трогать» — это разные вещи, и
API их различает.

**Ответ `200 OK`** — представление заметки после изменения.

**Ошибки:** `400 VALIDATION_FAILED`, `400 EMPTY_PATCH`, `400 INVALID_NOTE_ID`,
`401 UNAUTHENTICATED`, `404 NOTE_NOT_FOUND`.

Чужая заметка отвечает `404`, а не `403`. `403` подтвердил бы, что заметка с таким `id`
существует, и перебор идентификаторов превратился бы в разведку чужих данных. Подробнее — в
[ANSWERS.md](./ANSWERS.md), вопрос 3.

---

## 5. Удалить заметку

`DELETE /notes/{noteId}`

**Ответ `204 No Content`**, тела нет.

**Ошибки:** `400 INVALID_NOTE_ID`, `401 UNAUTHENTICATED`, `404 NOTE_NOT_FOUND`.

Повторное удаление отвечает `404`. Требование идемпотентности `DELETE` при этом не нарушается:
состояние системы после второго вызова то же самое. Отвечать `204` всегда — тоже допустимый
вариант, но тогда клиент не отличит «удалил» от «такого никогда не было», а это как раз тот
сигнал, который помогает ловить рассинхрон на клиенте.

---

## Чего в API нет намеренно

Совместного доступа к заметкам, тегов и папок, полнотекстового поиска, корзины и восстановления,
версий и истории изменений, экспорта. Каждое из этого меняет модель данных и права доступа —
добавлять их «на всякий случай» значит проектировать вслепую.
