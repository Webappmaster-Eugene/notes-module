# Инженерные решения

## 1. Что и почему сделано именно так

### Владение уезжает в условие запроса

```ts
await this.prisma.note.update({
  where: { id: noteId, userId },
  data: payload,
});
```

Поле where у метода update принимает не только уникальное поле, но и обычные фильтры. Если строка
с таким id есть, но user_id другой, Prisma отвечает ошибкой P2025 - тем же кодом, что и для
несуществующей записи. Репозиторий превращает P2025 в null, сервис - в 404.

Вариант, который я не выбрал: прочитать заметку, сравнить userId в коде и потом записать. Он хуже
по трём причинам. Лишний запрос. Окно между чтением и записью. И главное - проверка становится
отдельным условием, которое можно забыть написать в следующем методе. Здесь забыть нельзя, userId
обязателен в сигнатуре репозитория.

Что при этом делает Prisma внутри: находит строку по всему условию и выполняет UPDATE по
первичному ключу в одной транзакции. То есть это не буквально один SQL-оператор, но условие
владения исполняет база, а не приложение, и промежутка, в который заметка могла бы сменить
владельца, нет.

Если бы нужен был гарантированно один оператор, я бы взял `updateMany({ where: { id, userId } })`
и проверил число затронутых строк. Отказался, потому что updateMany не возвращает строку, и
понадобился бы второй запрос за телом ответа. Для операции, которая обязана вернуть обновлённую
заметку, это размен в худшую сторону.

### Патч пересобирается поле за полем

Функция pickUpdatableFields не копирует объект, а перекладывает два известных поля. Типы в
TypeScript стираются при компиляции, и объект, доехавший до сервиса, физически может нести userId.
На границе стоит whitelist вместе с forbidNonWhitelisted, но полагаться на один барьер в вопросе
владения не хочется. Тип патча свой, NoteUpdatePayload, а не `Prisma.NoteUpdateInput`: новое поле в
схеме не станет редактируемым автоматически.

### Значение null и отсутствие ключа - разные вещи

Тело `{"content": null}` очищает содержимое, тело без ключа content его не трогает. В DTO это
сделано через ValidateIf, а не через IsOptional. IsOptional пропускает и null, и отсутствие
значения, и тогда `{"title": null}` доехал бы до слоя данных и упал бы там на ограничении NOT
NULL, то есть клиент получил бы 500 вместо 400. Для title null отклоняется на проверке тела.

### Публичный метод сервиса принимает объект, а не два идентификатора подряд

Вызов выглядит как `update({ userId, noteId, patch })`. Два соседних параметра типа string типы не
различают: вызов `update(noteId, userId, patch)` скомпилируется и будет тихо ломать выборку.
Именованные поля убирают этот класс ошибок целиком. Внутри репозитория параметры позиционные, там
вызов один и он рядом с сигнатурой.

Более сильное решение - собственные типы для идентификаторов, чтобы перестановка стала ошибкой
компиляции. Не стал: для модуля такого размера это заметная церемония на каждой границе.

### Правило «патч не должен быть пустым» живёт в сервисе

Первым вариантом была своя проверка на DTO вида `@AtLeastOneOf(['title', 'content'])`. Отказался,
и причина неочевидная. Такие проверки регистрируются на свойство, а на title уже висит ValidateIf.
Условие ValidateIf отключает все проверки свойства, включая эту, то есть при отсутствующем title
правило молча не сработало бы. Такая мина хуже отсутствия проверки.

В сервисе правило заодно работает для любого вызывающего, не только для HTTP.

### Ошибка отдаётся в одном виде

Поля code и message, у ошибок проверки тела ещё details. Код машиночитаемый, сообщение для
человека в логе. Штатные ValidationPipe и ParseUUIDPipe отвечают каждый в своём формате, поэтому
обоим передан exceptionFactory. Иначе клиент получал бы три разные формы ошибки от одного
эндпоинта.

ParseUUIDPipe тут не только про аккуратность. Без него строка вроде abc доехала бы до Postgres и
упала на приведении к типу uuid, а клиент получил бы 500 вместо 400.

### Ответ собирается маппером, а не отдаётся строкой Prisma

Функция toNoteResponse перечисляет поля явно. Иначе любое новое поле в модели - служебный флаг,
хеш, внутренний счётчик - автоматически попадёт в публичный ответ.

### Prisma 6, а не 7

Седьмая мажорная версия уже вышла, но меняет генератор клиента и путь импорта. Для задания,
которое читают глазами, ценнее узнаваемый `@prisma/client` и конфигурация, совпадающая с
большинством живых проектов. Обновление здесь ничего не проверяет и только добавляет читателю
вопросов.

### UUID версии 7, а не 4

UUIDv7 возрастает во времени, поэтому вставки ложатся в конец индексного дерева, а не
разбрасываются по нему. На больших таблицах это заметная разница в фрагментации индекса и в
нагрузке на запись.

Оборотная сторона: идентификатор генерирует приложение, а не база, в SQL у колонки нет значения по
умолчанию. Значит, вставка в обход Prisma обязана передавать id явно. Альтернатива -
`dbgenerated("gen_random_uuid()")`, но это возврат к случайному v4, либо расширение pg_uuidv7 на
сервере.

### Тесты идут против подменённого клиента Prisma

Docker и живая база за рамками задания, поэтому `note.update` заменён стендом, повторяющим
поведение расширенного условия where и ошибки P2025. Это честный компромисс, а не полноценная
замена тесту против настоящей базы, см. следующий раздел.

## 2. Где решение всё ещё уязвимо

Настоящий SQL не проверен. Тесты доказывают, что userId попадает в условие запроса, и что логика
вокруг ответа правильная. Они не доказывают, что Postgres выполнит это условие так, как я ожидаю,
и что индекс действительно используется. Закрывается одним тестом против живой базы, и это первое,
что я бы добавил.

Поле updatedAt ставит приложение, а не база. Механизм @updatedAt работает только для записей через
Prisma. Ручной UPDATE в psql или миграция данных оставят метку старой. В системе, где в базу ходит
кто-то ещё, надёжнее триггер BEFORE UPDATE.

Пустой заголовок отсекается только на границе HTTP. Длины и правило «строка не из одних пробелов»
проверяет DTO, сервис проверяет лишь то, что патч непустой. Для второго транспорта, например
очереди или консольной команды, понадобится своя схема на его границе. Я бы вынес общую схему
проверки, а не дублировал проверки внутри сервиса.

Конфигурация контроллера не покрыта сквозным тестом. Настройки UsePipes и пайп для noteId
проверены поштучно: опции вынесены в общую константу и тестируются напрямую, пайп экспортирован и
тоже тестируется. Но что Nest действительно применит их к этому маршруту, проверил бы только
запрос через реальное приложение.

Нет ограничения частоты запросов. Код 429 в контракте описан, реализации нет: она за рамками модуля
и должна стоять выше, на уровне приложения.

Нет ограничения CHECK на непустой заголовок в самой базе. Prisma не умеет их описывать, нужна
ручная миграция. Тип `VARCHAR(200)` ограничивает только максимум.

Алиас `@/` требует внимания при встраивании. Внутри модуля импорты идут через paths из
tsconfig.json. Штатная сборка Nest на tsc алиасы в результате не переписывает, принимающему проекту
понадобится tsc-alias либо перевод импортов на относительные. Здесь это ни на что не влияет:
сборки нет, а тесты резолвят алиас через конфигурацию Vitest.

## 3. Что сознательно не делалось

Ограничения задания: без фронтенда, без регистрации и JWT, без Docker, не полноценный проект.

Аутентификация. Декоратор CurrentUserId читает `request.user`, который кладёт гард. Гарда нет,
есть точка, куда он встраивается. Декоратор при этом отказывает, а не возвращает пустое значение:
«пользователя нет» не должно превращаться в «пользователь с пустым идентификатором».

Остальные четыре эндпоинта спроектированы в [API.md](./API.md), кода нет: задание просило
реализовать один метод.

Файл main.ts и запуск приложения. Нет корневого модуля и стартового кода: модуль подключается в
существующее приложение, а не живёт сам по себе. Поэтому ValidationPipe объявлен на контроллере, а
не глобально, иначе его конфигурация оказалась бы в файле, которого в сдаче нет. По той же причине
в зависимостях нет `@nestjs/core`: модуль его не импортирует, стартовый код приносит принимающее
приложение. Пакеты reflect-metadata и rxjs оставлены, это обязательные зависимости
`@nestjs/common`.

Миграции. Вместо папки migrations в репозитории лежит `prisma/schema.sql`, сгенерированный
командой `prisma migrate diff`, см. `npm run prisma:sql`. Он показывает итоговый SQL с индексами,
но не требует поднятой базы.

Логирование, метрики, трассировка. В модуле такого размера это был бы шум.

## 4. Если бы была неделя вместо двух часов

Тесты против настоящего Postgres в контейнере: условие владения, план запроса списка через
EXPLAIN, поведение при удалении пользователя каскадом.

Оставшиеся эндпоинты, выборка по курсору с тестом на границу страницы и на одинаковые created_at.

Общая схема проверки входных данных на границах вместо DTO, привязанного к HTTP.

Доменные ошибки в сервисе плюс ExceptionFilter, который переводит их в HTTP. Сейчас сервис бросает
NotFoundException напрямую: для одного транспорта это прагматично, но привязывает домен к
фреймворку.

Правила доступа к строкам средствами Postgres как последний рубеж, если в базу ходит больше одного
сервиса.

Проверка версии при записи, то есть `version` в условии и ответ 409 при промахе, как только
появится сценарий редактирования одной заметки с двух устройств.
